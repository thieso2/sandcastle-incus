# The Dev Image: a Third Machine Template, and Why It Needed New Tenant-Creation Code

> Status: **accepted** (2026-08-11). Spec: `docs/spec/add-a-dev-base-image-ubuntu-26-04-fixed-b2qtk8g.md`. Builds on ADR-0022 (`/.sc` shared-scripts volume, reused unmodified). Partially opts out of ADR-0011 (Caddy HTTPS ingress) for Dev Image machines only.

## Context

Sandcastle had two Machine Templates (`base`, `ai`; both Debian 13, both `FROM sandcastle/base:latest` for `ai`). Neither gives a tenant a batteries-included *interactive* shell: no zsh, no prompt, no per-tool version manager, no context-usage status line. A developer who wants to work interactively inside a Sandcastle Machine assembled all of this by hand, every time, on top of `base` or `ai`.

The wish added a third template, `dev`: `FROM ubuntu:26.04` — a deliberately different OS lineage from `base`/`ai`'s Debian, not layered on top of either — carrying the minimum tenant plumbing to be a valid Sandcastle Machine (`systemd`, `openssh-server`, cloud-init) plus a fully provisioned interactive environment: zsh as the default shell, a starship prompt, a mise-managed toolchain, Claude Code + Codex CLIs with community skills, and a context-usage status line for both tools.

## Decisions

1. **Three Machine Templates, one build/publish pipeline.** `dev` plugs into the exact same `sc-adm image build/upload/sync` pipeline, `config.Admin.Images`, and `sc create --image` selection path that `base`/`ai` already use (`internal/images/plan.go`'s `PlanBuild`/`aliasForTemplate`/`templateAlias`, `internal/images/remote.go`'s `PlanRemoteBuild`, `internal/cli/admin.go`'s `remoteBuildTemplates`, `mise.toml`'s `image:dev:*` tasks folded into `image:all:*`). No new pipeline concept — a `dev` case, mirroring `ai`'s, added everywhere `base`/`ai` already branch. `Images.Dev` defaults to `DefaultDevImageAlias = "images:ubuntu/26.04"`, the same "stock public `images:` alias, zero-build fallback" pattern as `Images.Base`/`Images.AI` — **unverified against a live Incus `images:` remote** in the environment this shipped from; confirm with `incus image list images: ubuntu` before relying on it in production.

2. **`dev` does not install what it doesn't need.** No Gemini CLI (wish names only Claude Code + Codex), no Tailscale/Samba/CoreDNS/Docker-in-Docker (out of scope — satisfied by omission from the Dockerfile, no code changes elsewhere). `PlanBuild`'s `dev` arm requires Codex + Claude Code versions but not Gemini, unlike `ai`'s three-arg requirement.

3. **Minimum-tenant-plumbing scope is not "just a new Dockerfile" — it needed new tenant-creation code.** This is the finding that separates `dev` from a purely additive image: Caddy/TLS HTTPS ingress (ADR-0011) is applied **once per project**, not per image, via `V2DefaultProfileUserData` (`internal/tenant/create_plan_v2.go`) — every non-bare v2 machine in a project inherits it unconditionally, whenever `jinja && signerURL != ""`. There was no per-image or per-machine toggle before this wish. Satisfying "no public HTTPS ingress for Dev Image machines" therefore required a new lever, not a Dockerfile change:
   - `V2DevUserData(user, sshKey, domain string)` — a new function, structurally the same lever `V2BareUserData` already uses (INSTANCE-level cloud-init user-data, overriding the project profile's user-data per-instance) but **not** bare: a Dev Image machine keeps its login user, SSH key, and enabled sshd. It drops exactly the Caddy branch (`write_files`/`runcmd` for `sandcastle-generalize` and `sandcastle-caddy-setup`) — generalize goes with it, since generalize exists only to prep a machine for the leaf fetch caddy-setup then does. It keeps the `/.sc` boot shims (ADR-0022) so the Dev Image's zsh/agent-forwarding indirection still lands.
   - Detection of "this machine wants the Dev Image path" happens in `internal/cli/create_v2.go`'s `runCreateMachineV2`, the one place that has both the resolved `--image` value and `config.adminConfig.Images.Dev` in scope — `CreateMachineV2Request.DevImage` is an exact string match against the configured alias, threaded down as a plain bool (`internal/incusx/machine_create_v2.go`). `--bare` wins if both would apply (`DevImage: request.DevImage && !request.Bare`).
   - `uniqueImageAliases(admin.Images.Base, admin.Images.AI, admin.Images.Dev)` (`internal/tenant/create_plan_v2.go`) grows to include the Dev Image alias, so a freshly created tenant project's local Incus image aliases resolve `--image <dev-alias>` without a fully-qualified `<remote>:<fingerprint>` reference.

4. **No new SSH-agent-forwarding mechanism.** The stable-symlink indirection that keeps `ssh -A` working across `herdr`/`tmux` reattach is already shipped centrally by ADR-0022's `/.sc` payload — image-agnostic, applied via the profile/payload rather than baked per-image. The Dev Image's only obligation is to ship zsh pre-installed so `/etc/zsh/zshrc` exists for the shim's `append: true` cloud-init step to land in. This wish is verification-only for that mechanism (`docs/e2e-sc2.md` Phase 8e reuses Phase 6's existing PASS criterion, not a new one).

5. **`gh`'s own credential storage, never a hand-written token file.** Per-tenant git identity cannot be build-time (a shared image cannot hold per-tenant identity or credentials): `images/dev/git-identity-hook.sh`, sourced from the zsh rc, populates `user.name`/`user.email` from `gh api user` on first login, only when `gh auth status` already holds a credential and neither git value is already set — idempotent, never overwrites a hand-set identity. `gh auth login` itself stays a documented interactive first-run step; the image and the hook never hold or write a credential, and nothing credential-shaped is co-located with `~/.ssh/`.

## Relationship to other ADRs

- **ADR-0022 (`/.sc` shared-scripts volume): reused unmodified.** The Dev Image adds no new platform script and no new shim — it inherits the existing `/etc/ssh/sshrc` republish + guarded `/etc/zsh/zshrc`/`/etc/bash.bashrc` consume snippets exactly as `base`/`ai` do, because those shims are baked by `V2DefaultProfileUserData`/`V2DevUserData` at the profile/instance-data layer, not by the OCI image. `V2DevUserData` explicitly keeps `scShimWriteFiles` in its body for this reason.
- **ADR-0011 (Tenant TLS and Machine HTTPS Ingress): partially opted out of, for Dev Image machines only.** ADR-0011's model — every non-bare machine in a project gets a tenant-CA leaf and Caddy ingress — did not previously have an exception. `V2DevUserData` is that exception: a machine that is reachable (unlike `--bare`) but carries no public HTTPS surface. This is a narrower carve-out than `--bare`'s "no way in" — Dev Image machines are still fully reachable over SSH/the tenant tailnet, only the Caddy/TLS half of ADR-0011 is skipped.

## Consequences

- A third Machine Template is fully wired through the existing build/publish/select pipeline with no bespoke code paths — future templates (a fourth OS, a GPU-flavored image, etc.) have `dev`'s Go-side plumbing as a second data point beyond `ai`'s, reinforcing that the pipeline is genuinely N-template-shaped, not two-case special code.
- Ingress is now a per-instance decision, not purely a per-project one: `V2BareUserData` and `V2DevUserData` are both instance-level overrides of the project default profile, and any future template needing a different ingress posture has a precedent to follow rather than a new mechanism to invent.
- `CreateMachineV2Result.DevImage` plus `sc create` CLI messaging ("Dev Image: no Caddy/TLS ingress — SSH only.") make the ingress carve-out visible at creation time, matching the existing `Bare` result field's precedent — a Dev Image machine's `sc create` output no longer looks identical to a normal machine's, which would have silently under-reported the one thing this template exists to guarantee.
- Test coverage follows the existing pattern for instance-level user-data: `TestV2DevUserDataKeepsLoginDropsCaddy`/`TestV2DevUserDataBakesSCShims` (`internal/tenant/create_plan_v2_test.go`) and `TestV2ProfileSSHKeyPatternRoundTripsDefaultUserData`/`TestV2DevUserDataFollowsTheProfileIdentity` (`internal/incusx/machine_bare_v2_test.go`) assert properties of the rendered cloud-init string directly, no Incus involved — mirroring `TestV2BareUserDataHasNoWayIn`/`TestV2BareUserDataBakesBootShims`.
- Not validated against a live Incus deployment as of this ADR: an actual Dev Image build, the create-time Caddy-absence check (no process, no leaf, no `:443` answer), and the herdr/agent-forwarding reattach protocol on a real Dev Image machine. See `docs/e2e-sc2.md` Phase 8e and `implementation-notes.md` for what was verified instead (unit tests, source-level confirmation against `openai/codex@main` for the Codex status-line capability boundary) and why.
